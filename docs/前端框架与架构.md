# 前端框架与架构（React 19 路线）

> 状态：选型定稿。与《无服务器照片站架构设计》《存储与数据设计》《图片处理实现调研》配套。
> 本文定义前端框架栈、目录结构、数据流与代码组织，开发时以此为基线。

## 1. 决策记录

- **框架：React 19 + Vite + TypeScript**（用户确认）。纯 SPA，无 SSR（API 由 Pages Functions 提供）。
- 备选 Vue 3 的权衡已评估：Vue 对标 ChronoFrame（管理后台强），React 对标 Afilmory（展示层强）。
  单人自用 + 展示体验优先，选 React。
- **License 边界**（影响可抄范围）：
  - Afilmory 主仓库：**ANL v1.0**（Attribution Network License，限制性非标准协议）→ 只能参考功能思路，**不抄代码**
  - Afilmory `packages/webgl-viewer`：**单独 MIT** → 可借鉴代码（v2 查看器）
  - ChronoFrame：整体 **MIT**，但代码是 Vue → 参考逻辑与交互，用 React 重写
- 管理后台（Afilmory 没有 dashboard）：交互流程参考 ChronoFrame dashboard（上传页/任务状态/设置向导），
  用 Radix + Tailwind 自建。

## 3. 目录结构

```
apps/web/
├── index.html
├── vite.config.ts
├── functions/                  # ★ Pages Functions（Hono），与前端同项目部署
│   ├── api/
│   │   ├── auth.ts / photos.ts / site.ts
│   ├── _middleware.ts          # JWT 校验 + CORS + 限流
│   └── wrangler.jsonc          # D1/R2 binding、静态输出配置
└── src/
    ├── main.tsx / app.tsx      # 入口 + 路由表
    ├── routes.ts               # 路由配置（含 lazy）
    ├── types/                  # ★ 与 functions/ 共享的 API 类型（单一事实来源）
    ├── lib/
    │   ├── api.ts              # fetch 封装：类型安全、统一错误、自动带凭据
    │   ├── exif.ts             # exifr 封装（白名单字段提取）
    │   ├── convert.ts          # heic2any + canvas 转码/缩放管线
    │   ├── thumbhash.ts        # canvas → rgbaToThumbHash
    │   └── auth.ts             # 登录状态读写
    ├── stores/                 # jotai：authAtom / uploadQueueAtom / siteAtom
    ├── features/
    │   ├── gallery/            # 瀑布流、卡片、懒加载、日期分组
    │   ├── viewer/             # 详情页、图片查看器（v1 img 方案）
    │   ├── upload/             # 上传队列组件 + 预处理管线编排
    │   ├── admin/              # 管理列表、删除/编辑、设置页
    │   └── map/                # v2 地图
    ├── components/
    │   ├── ui/                 # 自建基础组件（Radix + Tailwind，shadcn 风格）
    │   └── layout/             # 页头、页脚、主题
    └── pages/
        ├── gallery.tsx         # /
        ├── photo/[id].tsx      # /photos/:id
        └── admin/              # /admin/*（login/upload/manage/settings）
```

**类型共享机制**：`types/` 下定义 `Photo`、`PhotoListResponse`、`UploadRequest` 等纯类型，
`functions/` 与 `src/` 通过 tsconfig `paths` 别名共同引用——API 契约只写一遍，两端编译各自校验。

## 5. 状态与数据流

### 5.1 职责划分

| 层 | 工具 | 管什么 |
| --- | --- | --- |
| 服务端状态 | TanStack Query | photos 列表、详情、settings；key：`['photos', cursor]` / `['photo', id]` / `['site']` |
| 客户端状态 | jotai | `authAtom`（JWT 存在性）、`uploadQueueAtom`（队列项+进度+失败重试）、`siteAtom`（站点配置缓存） |

### 5.2 缓存策略（单人体感"即时" + 低配额消耗）

- 列表：`staleTime: 60_000`；详情：`staleTime: 300_000`
- 上传/删除/编辑成功 → `invalidateQueries(['photos'])`（或按需局部更新）
- 列表用**游标分页**（服务端已定义 `?cursor=&limit=`），滚动加载，避免深偏移

### 5.3 上传流程状态机（features/upload）

```
queued → processing(file 预处理) → uploading → done
                        └─→ failed(可重试，clientId 不变幂等)
```

每项含 `clientId`（uuid）、`progress`（0-100）、`error?`。串行处理（控制内存），
失败单张重试（不重传已成功的）。

## 6. API 客户端设计（lib/api.ts）

```ts
// 统一 fetch 封装：自动带 cookie、JSON 编解码、错误归一化
async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`/api${path}`, {
    ...init,
    headers: { 'Content-Type': 'application/json', ...init?.headers },
  })
  if (!res.ok) {
    const body = await res.json().catch(() => null)
    throw new ApiError(body?.error?.code ?? 'unknown', body?.error?.message)
  }
  return res.json()
}
```

- 错误统一 `ApiError(code, message)`，UI 层按 code 分支（401 → 跳登录）
- 上传走独立 `uploadPhotos(formData, onProgress)`（XMLHttpRequest 才能拿上传进度，或 fetch+ReadableStream）
- 所有请求同源（Pages 域名），无需 CORS 配置

## 7. 图片查看器（v1 / v2 策略）

- **v1**：详情页 `<img src={lg|original}>` + CSS 过渡放大（沿用 `no-gl-grid` 的交互体验：
  点击放大、手势平移、滚轮缩放）。零库，足够单人浏览。
- **v2**：评估接入 Afilmory `webgl-viewer`（MIT）的平铺加载/手势方案，或继续自研。
  触发条件：v1 在大图（>1600px）平移缩放不流畅时再升级。

## 9. 开发规范

- 代码风格：eslint-config-hyoban + prettier（@innei/prettier），与 Afilmory 一致
- 组件命名：`components/ui/*` 纯展示无业务；`features/*` 内聚业务 + 局部状态
- 类型优先：API 契约只出现在 `types/`，页面组件不直接定义响应类型
- 提交：feat/fix/chore 前缀 + 中文描述（沿用 fanphoto 现有习惯）
