# 存储与数据设计（R2 图片存储 + D1 元数据）

> 状态：设计定稿。与《无服务器照片站架构设计》配套，本文细化存储层；
> **R2 对象布局以本文为准**（原架构文档 §4 的目录式布局已更新为本文的前缀式）。
>
> 参考实现：
> - ChronoFrame `server/services/storage/`：StorageProvider 接口（create/delete/get/getPublicUrl/
>   getSignedUrl/getFileMeta）、cdnUrl 优先的 URL 生成、presigned 直传、多 provider 运行时切换
> - Afilmory `packages/builder/src/plugins/`：thumbnail-storage（缩略图独立存储+URL 缓存去重）、
>   github-repo-sync（manifest+缩略图进 Git 仓库）

## 1. 总体职责划分

| 层 | 存什么 | 谁读写 | 免费额度 |
| --- | --- | --- | --- |
| **R2**（对象存储） | 图片字节：原图 + 3 档缩略图 + 视频（v2） | 上传时 Functions 写；访客浏览器直读（自定义域） | 10GB / 出站流量 0 费 |
| **D1**（SQLite） | 元数据：照片记录、EXIF JSON、设置 | 上传/管理 Functions 写；浏览 Functions 查 | 5GB / 50 万读·10 万写/天 |
| **Pages 静态** | SPA 代码本身 | — | 无限带宽 |

原则：**字节进 R2，事实进 D1**。D1 是唯一事实来源（照片列表/详情/编辑全查它），
R2 只提供不可变字节；URL 永远由 API 下发，前端不自行拼路径。

## 2. R2 图片存储设计

### 2.1 Bucket 与 Key 布局（前缀分区）

单 bucket（如 `afilmory-photos`），三种前缀：

```
originals/{photoId}.webp     # 转码后原图（≤2048px 上限）
thumbs/{photoId}/sm.webp     # 瀑布流卡片 400px
thumbs/{photoId}/md.webp     # 列表/详情 800px
thumbs/{photoId}/lg.webp     # 查看器 1600px
videos/{photoId}.mp4         # LivePhoto / Motion Photo 视频（v2）
```

选择前缀式而非 `photos/{id}/...` 目录式的理由：
- 删除一张照片：`originals/{id}.webp` + 按前缀 `thumbs/{id}/`、`videos/{id}/` list 一次拿全，原子性强
- 批量操作/巡检：按前缀扫（如清孤儿对象）成本低
- key 全部不可变（photoId 每次上传唯一），**同一照片绝不覆盖** → CDN 缓存永久有效，编辑只改 D1

### 2.2 访问方式：R2 自定义域直连（推荐）

```
图片 URL: https://cdn.photos.heabl.xyz/originals/{photoId}.webp
          https://cdn.photos.heabl.xyz/thumbs/{photoId}/sm.webp
```

- 绑定：R2 Bucket → Settings → Custom Domains，子域 `cdn.photos.heabl.xyz`（heabl.xyz 托管于 Cloudflare）
- **图片请求不经过 Pages Functions**：零函数配额消耗、无限带宽、R2 边缘 CDN 自带
- CORS：`<img>` 显示不需要 CORS；v2 若做 WebGL 查看器 fetch 原图像素，在 bucket 配 CORS 规则放行站点域即可
- 备选（不推荐）：Pages 站内 `/assets/*` 代理到 R2 —— 同域免 CORS，但每个图片请求消耗 Functions
  请求配额（10 万/天），且多一跳延迟

### 2.3 缓存策略（R2 对象上传时写入 httpMetadata）

| 路径 | Cache-Control | 理由 |
| --- | --- | --- |
| originals/thumbs/videos 全部 | `public, max-age=31536000, immutable` | key 不可变，永久缓存 |
| 删除后的边缘残留 | R2 源站删对象后返回 404（CF 默认不缓存 404） | 删除后很快全网 404，无需 purge |

重传场景：重复上传同文件生成**新 photoId**（幂等层拦截，见 §4），天然规避旧缓存。

### 2.4 上传写入路径（v1：Functions 中转）

```
浏览器 → POST /api/photos/upload（multipart）
  → Functions：JWT 校验 → 魔数校验（file-type）→ 大小限制（单文件≤50MB、单批≤20 张）
  → R2.put 全部对象（设 Cache-Control immutable）
  → D1 INSERT（client_id 幂等）
  → 失败回滚：删除已写 R2 对象
```

单文件 ≤50MB、单批 ≤20 张，远低于 Workers 免费计划请求体 100MB 上限，v1 不必 presign。
v2 若支持大视频/批量导入，升级为 ChronoFrame 同款 **presigned PUT 直传**（`getSignedUrl` +
`unhoistableHeaders: ['Content-Type']` 保证 CORS），Functions 只发签名。

### 2.5 存储预算

| 项 | 单张 | 1000 张 |
| --- | --- | --- |
| original.webp（≤2048px, q85） | ~0.8MB | 0.8GB |
| lg 1600px | ~0.6MB | 0.6GB |
| md 800px | ~0.2MB | 0.2GB |
| sm 400px | ~0.05MB | 0.05GB |
| **合计** | **~1.65MB** | **~1.7GB**（R2 免费 10GB，余量 8.3GB） |

去掉 lg 档可省 0.6GB（查看器用 original 直出，首屏稍慢），实现时二选一。

## 3. D1 数据存储设计

### 3.1 Schema（v1 定稿）

```sql
CREATE TABLE photos (
  id          TEXT PRIMARY KEY,               -- nanoid(12)
  client_id   TEXT NOT NULL UNIQUE,           -- 上传幂等键（浏览器生成的 UUID）
  title       TEXT NOT NULL DEFAULT '',
  description TEXT NOT NULL DEFAULT '',
  width       INTEGER,
  height      INTEGER,
  date_taken  TEXT,                           -- ISO 8601（EXIF 优先，文件名兜底）
  latitude    REAL,                           -- GPS，可空
  longitude   REAL,
  exif        TEXT NOT NULL DEFAULT '{}',     -- JSON：白名单字段（见图片处理调研 §2.4）
  thumb_hash  TEXT,                           -- base64 thumbhash
  tone_analysis TEXT,                         -- JSON（v2 直方图/影调）
  video_key   TEXT,                           -- v2 LivePhoto/Motion 视频对象 key
  created_at  INTEGER NOT NULL,               -- 入库时间戳(ms)
  updated_at  INTEGER NOT NULL
);
CREATE INDEX idx_photos_date_taken ON photos(date_taken DESC);
CREATE INDEX idx_photos_created  ON photos(created_at DESC);

CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL                         -- JSON
);
-- ('site', '{"title":"…","slogan":"…","author":"…"}')
```

- **client_id UNIQUE** 是幂等关键：重试/重复提交直接命中，不产生重复照片
- exif 存完整 JSON 而非拆列：单人查询模式只有"整条读"，无需按字段过滤
- latitude/longitude 独立成列：v2 地图点位查询直接 `WHERE latitude IS NOT NULL`
- 无 session 表（JWT 无状态）、无 queue 表（浏览器端处理，无服务端队列）

### 3.2 存储占用

1000 行 × 约 2KB（含 exif JSON）≈ **2MB**，D1 免费 5GB，余量巨大。
读压力：浏览列表/详情日均千次量级（免费 50 万读/天）。

### 3.3 迁移管理

- SQL 迁移文件放 `migrations/`（D1 原生格式，`wrangler d1 migrations apply DB --remote`）
- 提交流程：本地 `--local` 验证 → 生产 `--remote` 应用；由部署脚本/CI 执行（不依赖 Pages 构建）
- v1 结构极小，预留列已覆盖 v2 大部分需求，迁移频率很低

### 3.4 查询模式（游标分页）

```
-- 时间线列表：按 date_taken 倒序，游标 = (date_taken, id)
WHERE (date_taken < ? OR (date_taken = ? AND id < ?))
ORDER BY date_taken DESC LIMIT 50

-- 详情
SELECT * FROM photos WHERE id = ?
-- v2 地图点位（千行全扫可接受）
SELECT id, latitude, longitude FROM photos WHERE latitude IS NOT NULL
-- v2 搜索
SELECT id, title FROM photos WHERE title LIKE '%' || ? || '%' LIMIT 20
```

游标分页避免深偏移；id 做游标并列键保证唯一序。

### 3.5 备份与容灾（自用数据，必须）

| 数据 | 备份方案 | 频率 |
| --- | --- | --- |
| R2 图片 | Cloudflare 托管三副本（免操作）；可选配置 R2 到 R2 跨区域复制（不免费，单人跳过） | — |
| D1 元数据 | **每日导出 SQL → 写入 R2 `backup/` 前缀**（同一 bucket，成本 0） | 每日 |
| 双保险 | 每月手动 `wrangler d1 export` 下载一份到本地（或 GitHub 私有仓库，参考 fns-notes-backup 经验） | 每月 |

D1 每日导出实现：Workers **Scheduled Handler（cron 每日 03:00）** → `prepare("SELECT * FROM photos")`
→ 序列化 JSON → R2.put(`backup/d1-photos-YYYY-MM-DD.json`)。保留最近 30 份（或加生命周期规则）。
恢复：读备份 JSON → 逐行 INSERT（或整表 TRUNCATE 后重放）。

> 注意：R2 与 D1 同属一个账号，极端情况（账号被封）两者同失；
> 每月本地/GitHub 副本是真正意义的异地备份，建议保留。

## 4. 一致性协议（写入顺序与回滚）

| 操作 | 顺序 | 失败处理 |
| --- | --- | --- |
| **上传** | ① R2.put 全部对象（含视频）→ ② D1 INSERT | ②失败 → 删已写 R2 对象返回 500；client_id 冲突 → 查已有行幂等返回 200 |
| **删除** | ① D1 DELETE → ② 按前缀删 R2 对象 | ②失败容忍（孤儿对象，后台巡检清理；不影响用户） |
| **编辑** | 只写 D1（title/description） | R2 不动（key 不可变，无缓存问题） |
| **重传** | client_id 已存在 → 直接返回已有记录 | 不重复写、不覆盖对象 |

孤儿对象巡检（可选，v1 可不做）：cron 任务 list `thumbs/`、`originals/` 与 D1 的 id 集合比对，
删除不在库的对象。

## 5. 成本核算（单人 1000 张）

| 资源 | 用量 | 免费额度 | 结论 |
| --- | --- | --- | --- |
| R2 存储 | ~1.7GB（+备份 20MB/月） | 10GB | 免 |
| R2 出站流量 | 浏览图片流量（无限） | 0 费用 | 免 |
| R2 操作 | A 类上传万级/月、B 类浏览百万级/月 | A 100 万/月、B 1000 万/月 | 免 |
| D1 存储 | 2MB | 5GB | 免 |
| D1 读写 | 千级读/天 | 50 万读/天 | 免 |
| Functions | 上传+API 千级/天 | 10 万请求/天 | 免 |

**长期零成本成立。** 唯一的钱花在域名续费。

## 6. 与两个参考项目的存储对比

| 维度 | ChronoFrame | Afilmory | 本设计 |
| --- | --- | --- | --- |
| 元数据载体 | SQLite（photos 表） | manifest JSON 提交 Git 仓库 | **D1（SQLite 语义）** |
| 图片存储 | 多 provider 可切换（s3/local/openlist） | S3 原图 + 缩略图/manifest 进 Git | **R2 单 provider（自用无需切换）** |
| 上传方式 | presigned 直传 | 构建时批量拉取 | v1 函数中转 → v2 presign 直传 |
| 更新发布 | 上传即写库，SSR 实时 | 需重新构建部署才见新照片 | **上传即写库，API 实时** |
| 缩略图 | 存储 provider 同桶 | 独立 thumbnail-storage 插件可换存储 | R2 同桶前缀分区 |
| URL 生成 | cdnUrl 优先拼接 | storageManager.generatePublicUrl | API 下发完整 URL（cdn 子域） |

核心差异一句话：ChronoFrame 把"存储可切换"做成了功能（多 provider 管理界面），
Afilmory 把"构建产物可发布"做成了功能（Git 同步），本设计两者都不需要——
**R2+D1 固定组合 + 运行时查询** 对单人自用是最简形态。
